works". Branch `feat/nov-b` from `feat/release-nov` (5bf2a70) in `WA_agent-saas-s1-b`. Built test-first, small commits,

## What exists today (read 2 Nov)

- The chat is a sheet over the Clients screen, opened from a client's panel (`views/clients.js` → `openChat(code)`).
  There is no chat list: a chat is reached only through its client.
- Reading: `GET /dashboard/api/clients/:code/chat` (`src/web/routes/chat.ts` → `src/control/chatQueries.ts` `chatPage`).
- Sending: `POST …/chat/send` claims an outbox row, logs, then calls `sendGroupText` (`src/wa/groupSend.ts`), which
  takes the socket only from `gateway.groupSocket(groupId)` (approved group, open, not stopped). Rate limits: 3 s per
  group, 30 an hour.
- `tests/wa/sendScan.test.ts` keeps every Baileys outbound name (`chatModify` among them) out of `src/`, except the
  send in `groupSend.ts` and the sender phone; it pins the gateway's guard before `asGroupSendSocket` and the route's
  checks before `sendGroupText`.
- The store keeps all the delete needs: `messages.wa_id`, `from_me`, `sender_jid`, `ts`. Names: `people` (per client,
  by jid, with number and name). Key-value store: `getKv` / `setKv` (`src/store/kv.ts`).
- Baileys 7.0.0-rc14: `groupMetadata(jid)` (a read; the scan already lists it as read-only) gives `participants`
  `{ id, lid?, phoneNumber?, admin? }`; `chatModify({ delete: true, lastMessages: [{ key, messageTimestamp }] }, jid)`.

## The pieces, in landing order

### B1. Gateway additions (land first, so lane C can rebase on them)

Small, by group id, behind the same guard as `groupSocket` (approved, open, not stopped):

- `src/wa/groupMembers.ts` (new): `GroupMember { id, phoneNumber: string | null, admin: boolean }`,
  `membersOf(meta)` (normalises `participants`; never names), and a `GroupMembersSource` type.
- `src/wa/chatDelete.ts` (new): `ChatDeleteSocket { chatModify(...) }`, `asChatDeleteSocket(sock)`,
  `deleteGroupChat(source, groupId, last, timeoutMs)`: the group-id check, then the gateway's socket, then ONE
  `chatModify` delete with the last message's key and time (seconds); outcomes `deleted` / `failed` (surely not done:
  `not_a_group`, `whatsapp_not_connected`) / `unknown` (`timeout`, `delete_error`). Never retries; no error text kept.
- `src/wa/gateway.ts`: `SocketLike.groupMetadata`; `groupMembers(groupId)` (the guard, then one `groupMetadata`, 5 s
  cap, cached 5 min per group, `null` when it cannot ask); `chatDeleteSocket(groupId)` (the guard right before
  `return asChatDeleteSocket(sock);`). `GatewayLike` gains both as optional methods. The word `chatModify` never appears
  in `gateway.ts`.
- `src/wa/switchableGateway.ts`: forwards both to the current gateway (none: `null`), as `groupSocket` does.
- Tests: `tests/wa/gateway.test.ts` (each guard: not open, not allowed, stopped; the cache; a failing read gives null),
  `tests/wa/chatDelete.test.ts` (each outcome, the timeout, the key and seconds passed exactly), switchableGateway.
- `tests/wa/sendScan.test.ts`, a named exception locked like the send and history ones: `chatModify` is named only in
  `src/wa/chatDelete.ts`, called once, after the group check and `source(groupId)`; `chatDelete.ts` names no other
  outbound method; `asChatDeleteSocket(` appears once in `gateway.ts`, right after the guard; only `web/routes/chat.ts`
  calls `deleteGroupChat(`; only the gateways and the runtime name `chatDeleteSocket(`.

### B2. Group info panel (members)

- `GET /dashboard/api/clients/:code/chat/members` (approved client only): `{ groupName, members: [{ name, number, tag,
  admin }], known: true }`, or `{ known: false, reason }` when WhatsApp is not open or the read failed. `name` from
  `people` (by jid, then by number) or null; `number` formatted as WhatsApp shows it (+91 98xxx xxxxx) or null for a
  member WhatsApp gives no number for; `tag` the digits `@` uses. No jid, no LID, nothing else.
- `views/chat.js`: tapping the group's picture or name opens an info panel inside the sheet: the group name, the member
  count, each member (name, else number; admin marked). Tapping a member inserts `@Name` into the composer (only while
  sending is on). Every value through `esc()`.

### B3. Tagging

- Composer: typing `@` opens a member picker under the box (filtered as you type, arrow keys and Enter, tap on a
  phone); picking inserts `@Name `. Two members with the same name get the last 4 digits after the name in the picker
  and in the token, so a token is never ambiguous.
- On send the browser turns each picked `@Name` into WhatsApp's own form, `@<tag>`. The confirm dialog shows the text
  as the members will read it (`@Name`), and names who is tagged.
- `chat.ts` send: the body is unchanged (`uuid`, `text`, `replyTo`, `confirm`). When the text has `@<digits>` tokens, the
  route reads the members (B1) and mentions exactly the members whose tag appears; no member read possible: refused,
  nothing sent ("tags can't be checked right now"). The outbox keeps the text as sent; no schema change. Every existing
  rule stays: the switch, the confirm, the claim, the limits, the log before WhatsApp is asked.
- `groupSend.ts`: `sendGroupText(…, mentions)` puts `mentions` in the content (`{ text, mentions }`). The scan's counts
  for `groupSend.ts` stay as they are (one call, three names).
- Showing: in the chat, `@<digits>` tokens show highlighted, as `@Name` when the agent knows the member, else as the
  number. `chatPage` returns a small `names` map (tag → name) for the tokens on the page only.

### B4. Delete chat

- The chat's menu (the header's ⋮): Delete chat. The confirm names the group and says: it deletes the chat on your
  phone's WhatsApp and hides it here; it can't be undone; the agent's saved messages and tasks stay; the group stays
  approved.
- `POST /dashboard/api/clients/:code/chat/delete` with `{ confirm: true }`. Order, as for a send: the checks, then the
  log line before WhatsApp is asked, then `deleteGroupChat` with the newest stored message's key and time, then the
  outcome, then the audit line (`Chat deleted · Name (CODE)`, with the outcome; never a message's text).
- Hidden state, in the key-value store (no schema change): `chat_hidden_upto:<client id>` = the newest message row id
  at the delete (and the time, for the dashboard's own sent messages). The chat page shows only messages after it, so
  a new message in the group brings the chat back, as in WhatsApp. Saved messages, tasks, Activity and the client's
  approval are untouched.
- Outcomes: deleted → hidden, "Chat deleted"; failed → nothing hidden, the reason; unknown → hidden here, "It may not
  have been deleted on your phone: check WhatsApp". A second delete with nothing new since: no second request.
- Rate: one delete per group a minute (in memory is enough: it is a guard against a double tap, not a quota).
