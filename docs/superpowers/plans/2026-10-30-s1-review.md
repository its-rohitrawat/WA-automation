# S1 async conversion: a read-only review (30 Oct)

Reviewer: lane C (session c7), with fresh eyes. Reviewed: `src/` on `feat/saas-s1` at 1fd5004. Tests and lane C's own
folders (`src/platform`, `src/runtime`, `src/migrate`) were left out. No file other than this one was changed.

**Result: one confirmed bug, one behaviour change, one hardening point, and a watch list for S1.12 and S1.15.** The
rest of the conversion checks out clean against the six known bug families: every converted call site is awaited,
returned or handled.

---

## How it was checked

TypeScript 7 (the native compiler) has no JavaScript API for a checker, so the review used rolldown's TypeScript parser
(`rolldown/parseAst`, already installed) for syntax, and the code itself for meaning. The scripts are in lane C's
scratchpad, not the repo.

1. **Every function and method that became async in S1:** 304 names, taken from the diff 450f822..HEAD. Each call site
   in `src/` was printed and read when it was not awaited, returned, voided, chained with `.then`, `.catch` or `.finally`,
   or inside `Promise.all`.
2. **A syntax scan of every call to an async name.** It covers the 539 names declared async or returning `Promise` in
   `src/`. Plain calls were resolved through the file's imports to the real function; a method name was counted only
   when no sync definition shares it. Each call was classified by its context:
   - a boolean test (`!`, `if`, `?:`, `&&`, `||`, `??`);
   - a comparison or concatenation, or a template literal;
   - an argument, an array or object member, or a spread;
   - a member access on the promise;
   - a floating statement, a `void`, or a statement inside `try`;
   - `return` inside `try` (the catch misses the rejection);
   - `.then` with no `.catch`;
   - a stored promise;
   - the outer handle used inside `x.tx((q) => …)`.

   It found 146 sites, each read by hand. Most were same-named sync methods (`status()`, `send()`, `Map.get`) or still
   synchronous `raw` calls, which S1 allows until S1.15.
3. **Async callbacks handed to something that ignores their promise:** timers, `.on`, `forEach`, `onEvent` and
   `onStatus`. Also every interface field typed `(...) => void` (28 of them) checked for an `async` value.
4. **Transactions:** for each file, the transaction calls at 450f822 compared with now. Every file whose count changed was
   read in full (`control/meetingActions.ts`, `web/routes/auth.ts`, `cli/corrections.ts`, `health/uptimeLog.ts`,
   `wa/authState.ts`).
5. **By hand:**
   - the Baileys event chain (`wa/gateway.ts`, `#deliver` and `#handOver`), the history backfill and the ingest;
   - the publisher (`output/drive.ts`);
   - `app.ts`'s tick and stop;
   - `main.ts`'s start order (awaits against the signal handlers) and stop chain;
   - every `void` call in `src/`.

**Limits:**
- Without types, a method whose name is shared by a sync and an async definition is only caught when its object looks
  like a database handle.
- Generic names (`get`, `run`, `list`, `status`, …) were skipped in pass 1, and were covered by passes 2 to 5 instead.

## Findings, by severity

### 1. Medium: a promise tested as a boolean. `src/media/processor.ts:557` (lane B, `media/**`)

```ts
#noteUnansweredCopy(row: MediaRow, e: unknown, at: string): void {
  const copy = voiceCopyOf(e);
  if (copy === null || !this.#noteCopy(row, copy, at)) return;   // #noteCopy is async since S1.8
  …
  void forgetVoiceCopies(db, voice, log, { mediaId: row.id, clock }).catch(…);
}
```

- **Why it's wrong:**
  - At 450f822 `#noteCopy` returned a `boolean`. S1.8 (99bfa2a) made it `async #noteCopy(): Promise<boolean>` and added
    the `await` at its other call, line 401, but not here.
  - `!promise` is always `false`, so the early return never happens.
  - `forgetVoiceCopies` for this file then starts without waiting for the note to be written.
- **What goes wrong:**
  - A provider (a paid speech service) keeps a copy of a voice note whose answer could not be read. The prompt deletion
    is meant to run only once the row in `media_stt_forget` exists.
  - **On SQLite today it works by luck:** `noteMediaForget`'s write enters the FIFO queue before `forgetVoiceCopies`'s
    first read.
  - **On Postgres (S2), it's a race:** the two run on different pooled connections, so `forgetVoiceCopies` can read before
    the note exists. It then deletes nothing, and the copy stays at the provider until the hourly sweep. That is customer
    voice data kept longer than intended.
  - When the note fails, the deletion is started anyway. That is harmless, since it finds nothing, but it isn't what the
    code says.
- **The fix is for lane B:**
  - make the method `async`, or wrap its body as
    `void (async () => { if (!(await this.#noteCopy(row, copy, at))) return; … })().catch(log)`;
  - add a test that fails when the note fails, and that checks the order on a slow note.

### 2. Low: history answers now interleave with live events. `src/wa/historyBackfill.ts:77-78`, `:198-235` (lane B)

- **What changed:**
  - At 450f822, `#onAnswer` was synchronous: a whole on-demand history answer was ingested in one turn, between two live
    events.
  - Now `#onAnswer` awaits each `ingest(e)` on its own chain (`#answers`), while the gateway's live events run on
    `#handOver`'s chain. Both call the same `handleEvent`, so a live event can land in the middle of a history answer.
- **The concrete effect:**
  - `found` is worked out as `messageCount(after) - messageCount(before)` around the loop. A live message that arrives
    for the same group during the answer is counted as an "earlier message found". The dashboard's "N earlier messages
    read" note (`onHistoryRead`) can be too high.
  - `src/wa/ingest.ts:53` says "The gateways hand events over one after another, waiting for each, so they are stored in
    order". That no longer holds for history events.
  - The data itself is safe: each message's writes are one transaction, and `INSERT OR IGNORE` makes a double delivery
    harmless.
- **A possible fix (lane B):**
  - count only what the answer's own inserts reported as new (`insertMessage` returns `isNew`), not the table
    difference;
  - or run history answers through the gateway's `#handOver` chain;
  - and correct the comment in `ingest.ts`.

### 3. Low (hardening): an answer chain with no catch. `src/wa/historyBackfill.ts:78` (lane B)

```ts
o.gateway.onHistory((a) => {
  this.#answers = this.#answers.then(() => this.#onAnswer(a));
});
```

- **The risk:**
  - If `#onAnswer` ever rejects, `#answers` stays rejected. Every later answer is skipped without a word, since `.then`
    on a rejected promise never runs its callback, and each skipped link is an unhandled rejection. On Node 24 the default
    for an unhandled rejection is to end the process.
  - Today `#onAnswer` catches almost everything. Only its tail, after the `try` (`out.timeout.cancel()`, `#soon`), is
    unguarded, and those are synchronous and unlikely to throw.
- **The fix (lane B):** `this.#answers = this.#answers.then(() => this.#onAnswer(a)).catch((err) => log.error(…))`. It's
  one line.

## Watch list: sync calls with the outer handle inside a transaction (S1.12 and S1.15)

These are **correct today**. The callee is still synchronous on `raw`, which S1 allows inside the transaction's own
async context, and on the same connection, so the write is inside the transaction.

Each one must take the transaction handle `q` when its callee becomes async. Otherwise:
- on SQLite it throws `TxMisuseError` (the 149-failure family);
- on Postgres the write lands on another pooled connection, **outside the transaction**.

| Site | Call | Callee now | Lane |
|---|---|---|---|
| `src/brain/reconciler.ts:310`, `:407` | `getClient(db, …)` inside `db.tx` | sync (`store/clients.ts`) | B |
| `src/control/taskActions.ts:181` | `requestRebuild(db, now)` inside `db.tx` | sync (`cli/corrections.ts`, kv) | B |
| `src/report/scheduler.ts:331-332` | `getKv(db, …)`, `setKv(db, …)` inside `db.tx` | sync (`store/kv.ts`) | A |
| `src/config/prioritySettings.ts:201` | `setKv(this.#db, …)` inside `this.#db.tx` | sync | A |
| `src/cli/commands.ts:594` | `setKv(db, …)` inside `db.tx` | sync | A |
| `src/cli/corrections.ts:134`, `:144`, `:146`, `:153`, `:155`, `:194` | `requestRebuild`, `setPhase`, `clearPhaseLock` with `db` inside `db.tx`/`inTx` | sync | A |
| `src/cli/meetings.ts:103`, `:115`, `:140` | `requestRebuild(db, now)` inside `db.tx` | sync | A |
| `src/assistant/proposals.ts:186-187` | `applyTaskAction(d.db, …, ctx, q)` | async, and uses `q` for its own transaction; `d.db` only reaches the sync kv write above | A |
| `src/wa/historyBackfill.ts:156`, `:168`, `:190`, `:227`, `:240`, `:254` | `saveBackfill(db, …)` (not in a transaction) | sync (`store/historyBackfill.ts`) | B |

The last row has no transaction. But when `saveBackfill` becomes async, each of those six calls needs an `await`:
- `:190` and `:240` sit in a `try` whose `catch` would then miss the rejection;
- `#finish` (`:254`) is called right before `onFinished`, which reads what it wrote.

A grep for `saveBackfill(` will find them all.

## Checked and clean

- **Booleans, comparisons, templates, containers:** no other promise tested, compared or stringified, and none put in a
  `Set`, `Map`, `Array.from` or `JSON.stringify` (all 304 S1 names, pass 1).
- **`void` calls (27 in `src/`):** each is a never-rejecting chain, has its own `catch`, or calls a function that catches
  everything inside (`tick`, `#beat`, `#step`, `#timedOut`, `endQuietly`, `handle`, `uploader.run`,
  `reportRunner.tick`).
- **`.then` chains:**
  - `app.ts:296`, `:389`, `:407` and `:716` follow `safelyAsync`, which catches, with a sync `schedule()`;
  - `main.ts:370` has its catch first, and `keepUptime` catches;
  - `main.ts:463` catches first, then exits;
  - `groupsWriter.ts:84` chains on a `tail` that cannot reject.
- **`return` inside `try` in async functions:** none returns an un-awaited call.
- **Async callbacks to ignoring callers:** none unguarded. `cli/commands.ts:139` is awaited by the gateway's
  `#handOver` inside its `try`. The two `.map(async …)` calls are inside an awaited `Promise.all`. No `(...) => void`
  field is given an `async` function.
- **Transactions that moved:**
  - `control/meetingActions.ts` now passes its audit line into each command's own transaction (`inTx`, awaited);
  - `web/routes/auth.ts` keeps the session write and its audit row in one `d.tx`;
  - `cli/corrections.ts` keeps every transaction through `inTx`.
- **Start and stop:**
  - `main.ts` awaits nothing between `app.start()` and installing `SIGINT` and `SIGTERM` (the earlier finding is fixed);
  - the awaits before `app.start()` existed before S1;
  - the stop chain catches at every step.
- **Ordering in `app.ts`'s tick:**
  - `clientIdsWithUnprocessed` is read first and awaited after the synchronous kicks, with no turn in between, so its
    rejection is caught by the tick's `try`;
  - the publisher's single-flight with one follow-up (`output/drive.ts`) is unchanged by S1.
- **Stored promises:** `control/groups.ts:63`, `report/liveReport.ts:77`/`:93` and `report/scheduler.ts:254` are each
  awaited in a `try` on the next lines.
